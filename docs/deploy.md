# Docker, CI и публичное демо (этап 5)

## Docker

`Dockerfile` — два шага: Node.js собирает дашборд, в итоговый образ на `python:3.12-slim` попадают только
бэкенд, документы, evals и статика дашборда. Процесс работает не от root, есть `HEALTHCHECK` на `/health`.
При старте контейнер индексирует документы (неизменённые пропускаются) и запускает API с дашбордом.

```bash
cp .env.example .env   # пароли базы и ANTHROPIC_API_KEY
make up                # docker compose up -d --build --wait → http://127.0.0.1:8000/
make down
```

`docker-compose.yml`: сервис `db` (Postgres 16 + pgvector, схемы и демо-данные при первом старте) и `app`
(агент). Внутри compose агент всегда ходит в `db`, даже если в `.env` указана внешняя база. Отчёты evals и
журнал заглушки Битрикс24 лежат в томе `appdata`. На Windows — `windows\docker-up.bat`.

## CI

`.github/workflows/ci.yml` на каждый push и pull request:

| Задача | Что проверяет |
|---|---|
| Backend | схема и демо-данные накатываются `db/apply.sh` на настоящий Postgres 16 + pgvector; ruff; все pytest, включая интеграционные (права `agent_reader`, поиск по документам, эталонный SQL evals) |
| Frontend | `npm ci`, проверка типов, vitest, сборка |
| Docker | сборка образа и smoke-тест: образ стартует рядом с базой, отвечает `/health`, `/meta` и отдаёт дашборд |

Модель в CI не вызывается — тесты на заглушках, ключи не нужны. Качество на настоящей модели проверяют evals
(вручную: `make evals` или кнопка в дашборде), потому что прогон стоит денег.

## Режим публичного демо

Чтобы дать ссылку работодателю, не рискуя ключом и бюджетом, — `DEMO_MODE=true` в `.env`:

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `DEMO_ACCESS_CODE` | — | код доступа (латиница и цифры); без него чат не отвечает, дашборд сам спросит код |
| `DEMO_DAILY_BUDGET_USD` | 2 | дневной лимит на модель по фактической стоимости ответов; дальше — «попробуйте завтра» |
| `DEMO_REQUESTS_PER_HOUR` | 30 | лимит вопросов с одного IP в час |
| — | — | запуск evals через API выключен (история прогонов видна), Битрикс24 — только заглушка |

Остаток дневного лимита виден в шапке дашборда. Дополнительно стоит поставить месячный лимит расходов
на сам ключ в консоли Claude Platform.

## Где разместить демо

Нужны: контейнер с агентом (порт 8000, переменная `PORT` поддерживается) и Postgres с pgvector.

- **VPS с Docker** (любой провайдер, в том числе казахстанский): `git clone`, `.env` с `DEMO_MODE=true`,
  `make up`, перед ним — обратный прокси с HTTPS (Caddy или nginx). Самый простой и предсказуемый по цене вариант;
  база живёт рядом в compose.
- **PaaS для контейнеров** (Render, Railway, Fly.io и т.п.) + управляемый Postgres с pgvector (Supabase, Neon):
  схема и данные — `DATABASE_URL=… AGENT_DB_PASSWORD=… ./db/apply.sh`, у контейнера — `DATABASE_URL`,
  `AGENT_DATABASE_URL` (для пулера Supabase — с именем роли в его формате), `ANTHROPIC_API_KEY`, `DEMO_MODE=true`.

В демо нет реальных персональных данных — всё синтетическое. Для настоящего внедрения размещение базы и модели
(в контуре компании, на площадке в Казахстане, self-hosted модель) решается вместе с юристом заказчика по закону о ПДн.
